# 项目架构与维护规范

## 1. 设计目标

本项目同时包含真实机器人控制、数据处理和模型训练。最重要的原则是：

1. 安全逻辑只有一个实现来源，不能复制到多个脚本后分别修改；
2. 用户实际执行的入口保持稳定、简短，并在 README 中给出完整命令；
3. 数据、模型、日志和报告分开保存，任何脚本都不能静默覆盖旧实验；
4. 修改必须可追溯：代码变更同步更新 `CHANGELOG.md`，流程变化同步更新 README；
5. 先复用现有函数，再增加新函数；只有出现明确的新职责时才增加新文件。

## 2. 功能分层

```text
用户入口层
  record_*.sh / train_*.sh / run_*.py
        ↓
任务编排层
  参数检查、路径生成、阶段切换、数据标签
        ↓
共用安全与控制层
  safe_lerobot_cli.py
        ↓
LeRobot 与硬件驱动层
  /home/user/ljn/lerobot
```

数据训练链：

```text
BC 示范 → BC checkpoint
              ↓
策略 rollout + 人工介入标签
              ↓
合并数据 → 生成逐帧训练权重 → 加权微调 → 新 checkpoint
```

## 3. 目录职责

- `scripts/`：稳定的可执行入口和当前共用实现。入口文件名使用动词开头：
  `record_`、`train_`、`run_`、`prepare_`、`compute_`、`check_`、`audit_`。
- `data/barbell/`：正式 BC 数据和已经整理好的训练数据集。
- `data/rl_rollouts/`：未经合并的策略 rollout，每轮一个时间戳子目录。
- `outputs/`：checkpoint，每个实验一个新目录，禁止覆盖。
- `reports/`：可重建的审计、推理结果和分析结果。
- `logs/`：终端训练日志。
- `docs/`：架构、研究依据和较长的设计说明。

暂时不移动现有 `scripts/` 入口，因为这会使已经记录的命令全部失效。后续当
两个以上入口需要同一段实现时，再把共用代码提取到 `src/barbell_task/`，
入口脚本只负责解析参数并调用共用模块。

## 4. 每次修改的完成条件

一次修改只有同时满足下列条件才算完成：

1. 代码包含解释“为什么”的中文注释，避免逐行翻译式无效注释；
2. Python 运行 `py_compile`，Shell 运行 `bash -n`；
3. 涉及数据转换时使用小型合成数据验证边界情况；
4. 涉及机械臂时先验证无动作路径，再由操作者在急停旁做真实测试；
5. 在 `CHANGELOG.md` 登记影响和验证结果；
6. 如果命令、按键、默认路径或参数变化，同步更新 README。

## 5. 实验可追溯规则

- 数据目录、训练输出和报告目录使用不可重复的实验名或时间戳。
- 训练前保存：基础 checkpoint、数据集路径、标签路径、超参数和代码日期。
- 不删除原始数据与正式 checkpoint；清理前先列出精确目标并人工确认。
- 对算法性假设使用“实验性”标记，不能把启发式权重称为已学习出的真实价值。
- 建议下一步在 `/home/user/ljn` 初始化 Git；大型数据和 checkpoint 用
  `.gitignore` 排除，仅追踪代码、README、配置和变更记录。
